# GPU vs CPU Pantograph Lift transform: crossover measurement

Generated by `bench/gpu_crossover.py`, measuring `scissorc bench-transform` directly -- this isolates the forward transform itself (what the CUDA kernel actually accelerates) from the CPU-sequential entropy-coding stage that follows it in a full `compress()` call and runs identically on both paths. All numbers below are real measurements from this run on this machine (RTX 2060 Max-Q laptop GPU, CUDA 13.2).

## One-time GPU wake / context-creation cost

This laptop GPU idles down to a low-power state (`nvidia-smi` shows P8, ~4W) when unused. The first CUDA call after ~8s idle pays a real, fixed cost to wake it and create a context -- independent of input size. This is not a bug and not amortizable within a single one-shot CLI process; it is the reason a single `scissorc compress --gpu` on one small file can look far slower than the CPU path, while back-to-back GPU calls (a batch/service workload) do not pay this cost repeatedly.

- First GPU call after idling: **1218.0 ms** (n=1,000,000, gpu_used=True)
- Immediately following GPU call (same process launch pattern, GPU already awake): **94.6 ms**

## Warm sustained throughput (back-to-back calls, GPU already awake)

Each size is run 3 times back-to-back for both CPU and GPU immediately beforehand (best-of-3), representing a batch/service workload rather than an isolated one-shot call.

| n (elements) | CPU (ms) | GPU (ms) | GPU vs CPU |
|---:|---:|---:|---:|
| 100,000 | 0.652 | 85.361 | 0.01x |
| 1,000,000 | 5.436 | 89.978 | 0.06x |
| 4,000,000 | 21.693 | 103.453 | 0.21x |
| 16,000,000 | 82.897 | 160.240 | 0.52x |
| 64,000,000 | 303.149 | 396.174 | 0.77x |
| 256,000,000 | 1180.560 | 1929.240 | 0.61x |

## Sustained repeated calls within one warm process

The table above launches a fresh `scissorc` process per measurement, so every GPU call pays its own allocation cost and, if the GPU had idled since the last call, its wake-up cost too. A real batch/service workload processes many inputs from one long-lived process instead. This table calls `scissorc bench-transform <n> --repeat 8` (or 5 for 256M) so multiple calls share one warm CUDA context and GPU clock state, reporting the steady-state average of calls 2+ (call 1 still pays whatever the GPU's clock/idle state happened to be) for both CPU and GPU.

| n (elements) | CPU steady-state (ms) | GPU steady-state (ms) | GPU vs CPU |
|---:|---:|---:|---:|
| 100,000 | 0.686 | 2.203 | 0.31x |
| 1,000,000 | 5.564 | 8.658 | 0.64x |
| 4,000,000 | 21.998 | 25.198 | 0.87x |
| 16,000,000 | 82.551 | 84.650 | 0.98x |
| 64,000,000 | 302.874 | 301.831 | 1.00x |
| 256,000,000 | 1193.210 | 1199.310 | 0.99x |

- In sustained use (steady state, GPU clocks already ramped up), GPU beat CPU outright at 1/6 sizes tested in this run: 64,000,000. The rest were within a percent or two either way -- run-to-run noise at this point, not a clear win for either side. This is a materially different, more favorable picture than the one-shot-per-process table above, and it's the fairer comparison for how this would actually be deployed (a service handling many requests, not one process per file).

## Honest conclusion (one-shot-per-process table)

- Across every size tested here, the CPU path was still faster once the GPU is warm. This is an honest negative result, not a hidden one: even with the GPU-resident rewrite (no per-level host<->device round trips), the residual/parameter buffers copied back at the end and the fixed per-kernel-launch overhead across ~log2(n) sequential levels apparently still outweigh the parallel work being done at these sizes on this GPU. Larger inputs than tested here, or a GPU with higher memory bandwidth / more SMs, may cross over; that is not claimed here because it was not measured here.

- The one-time wake cost above means a single ad-hoc `scissorc compress --gpu` on one file is very likely a net loss versus the CPU path -- the GPU path only makes sense for sustained/batch use where many calls amortize one wake-up, which is exactly the pattern this repo owner's other GPU-resident projects (CKKS homomorphic encryption, LiDAR preprocessing) are built around.

- There is a practical upper size limit on this GPU: a one-off probe at 400,000,000 elements (needing roughly 3 buffers of that size, ~6.4GB, against this card's 6GB) hit a genuine CUDA resource error and `pantograph_lift_forward_cuda` correctly returned `false`, and `compress()`'s automatic CPU fallback handled it transparently -- this is the graceful-degradation design actually being exercised under real resource exhaustion, not just a theoretical code path. 256,000,000 elements (the largest row above) is close to the practical ceiling on this card; a GPU with more VRAM would push it further.
