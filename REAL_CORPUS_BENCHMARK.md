# CSA vs. real market competitors on a real corpus

Generated by `bench/real_corpus_benchmark.py`. The corpus is 18,120,520 bytes of real, concatenated C++ source files from a large local repository (OpenFHE) -- not text written or generated for this benchmark, and not tuned to flatter any compressor. This is the credibility check `BENCHMARKS.md`'s synthetic shapes and `USE_CASES.md`'s realistic-but-generated scenarios can't fully provide. CSA is run at all three speed/ratio levels it exposes (`--level fast|balanced|high`), the same tradeoff every production LZ compressor exposes (gzip -1..-9, zstd -1..-22) -- "is it good" depends on which point on that curve you need.

## Honest verdict

- Even at `--level high`, CSA does not beat the best reference here (lzma -9): 1,907,052 bytes vs 1,681,564 bytes (13.4% larger). Real source code has exactly the kind of medium-range, high-order repeated structure (identifiers, indentation, common phrases) that LZMA/zstd's optimal-ish parsing and larger match finders, and bz2's Burrows-Wheeler Transform, are specifically built to exploit, and this codec's lazy-matching LZ + order-1 entropy model currently isn't. (CSA's BWT mode, which wins big on smaller realistic files -- see USE_CASES.md -- is genuinely tried here too, not skipped: it's cheap enough since switching to a linear-time suffix-array construction (see DESIGN.md) to run unconditionally at this size, but it still doesn't win on real source code specifically -- LZ's exact-repeat matching simply covers this corpus's redundancy better.) Closing this specific gap needs the other named future work item, optimal cost-based LZ parsing.

- At `--level fast`, CSA beats both gzip and bz2 on size (2,036,709 bytes) while compressing faster than lzma (2.66s vs 4.20s) -- a real, honest position on the speed/ratio curve, not a win on every axis at once.

- CSA `--level fast` beats zstd -3 (default) on size (2,036,709 vs 2,933,235 bytes) -- but zstd -3 (default) did it in 0.05s (CSA took 2.66s at that level). zstd's default level alone compresses this whole 18MB corpus in a fraction of a second; matching its ratio is the easy part.

- The more important comparison: **zstd -19 (high) beats CSA `--level high` on both size and speed at once** (1,708,866 vs 1,907,052 bytes, 11.6% smaller, in 5.06s vs CSA's 31.48s -- 6.2x faster). That's the honest measure of the actual gap to a modern production compressor: not just ratio, but the whole speed/ratio curve simultaneously. Closing it needs the things DESIGN.md's future work already names (optimal parsing, a smarter match finder) plus real performance engineering zstd has had years of -- not a claim this project makes.
