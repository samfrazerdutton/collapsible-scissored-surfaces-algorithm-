# CSA vs. gzip/bz2/lzma on a real corpus

Generated by `bench/real_corpus_benchmark.py`. The corpus is 18,120,520 bytes of real, concatenated C++ source files from a large local repository (OpenFHE) -- not text written or generated for this benchmark, and not tuned to flatter any compressor. This is the credibility check `BENCHMARKS.md`'s synthetic shapes and `USE_CASES.md`'s realistic-but-generated scenarios can't fully provide. CSA is run at all three speed/ratio levels it exposes (`--level fast|balanced|high`), the same tradeoff every production LZ compressor exposes (gzip -1..-9, zstd -1..-22) -- "is it good" depends on which point on that curve you need.

| CSA --level balanced (LZ dictionary matcher) | 1,950,894 | 89.2% smaller | 5.14s | PASS |

CSA decompress time (all levels, same format): ~0.13s

## Honest verdict

- Even at `--level high`, CSA does not beat lzma's ratio here: 1,907,052 bytes vs 1,681,564 bytes (13.4% larger). Real source code has exactly the kind of medium-range, high-order repeated structure (identifiers, indentation, common phrases) that LZMA's optimal parsing and larger match finder, and bz2's Burrows-Wheeler Transform, are specifically built to exploit, and this codec's lazy-matching LZ + order-1 entropy model currently isn't -- see DESIGN.md's future work (optimal parsing, a BWT-based mode) for what closing it would actually require.

- At `--level fast`, CSA beats both gzip and bz2 on size (2,036,709 bytes) while compressing faster than lzma (1.45s vs 4.35s) -- a real, honest position on the speed/ratio curve, not a win on every axis at once.
