Compress Spatial Reality at the Edge.

Autonomous drones, robots, and AR/VR headsets generate 6-DOF pose streams and LiDAR point clouds faster than constrained RF, satellite, or degraded 5G links can carry them. This codec understands the kinematics of that data — position, rotation, point geometry, adaptive per-block precision — instead of treating it as an undifferentiated byte stream.

C++ spatial codec. WebAssembly runtime. Zero-server execution — the compiled core runs inside a Web Worker in this browser tab; nothing you feed it is ever uploaded anywhere.

Where This Fits

Where CSA has a potential fit

  • 6-DOF pose streams (drones, robots, AR/VR headsets) — beats general-purpose compressors on three independent real ground-truth datasets, lossless.
  • Real ROS2 PoseStamped telemetry — MCAP's own default zstd container is measured larger than raw packed data on 2 of 3 real datasets; CSA is smaller on all three.
  • Bandwidth-constrained links (LoRa, degraded 5G, satellite) where every byte saved is transmit time saved — particularly interesting when the data is already spatial/kinematic in shape.
  • GPS-style 2D tracks — beats lzma -9 and even a purpose-built lossy format (Google Encoded Polyline) while staying exact.

Where CSA loses — honestly

  • Specialized point-cloud formats: LASzip (industry-standard LAS/LAZ) beats CSA on the same real LiDAR scan, 87.8% vs. 84.0% smaller, and is far faster. WHY_NOT_ZSTD.md →
  • Aggressively-quantized lossy point clouds: Draco at its roughest setting produces a smaller (lossy) file than CSA's exact result — expected, since lossless can't beat sufficiently aggressive lossy.
  • Arbitrary files with no spatial structure — logs, source code, JSON. CSA's general-purpose fallback loses to zstd -19 on both size and speed on a real 18MB C++ source corpus. This isn't a defect; it's the trade-off of a codec built around kinematics instead of generic entropy coding.

Why This Isn't Just gzip

Schema-less
Point/pose/general shape is inferred directly from the data itself — no protobuf or JSON schema to define or version.
No GC pauses
The compression hot path runs in WASM linear memory with manual malloc/free, not JS object allocation — nothing for a garbage collector to pause on mid-compression.
Off the main thread
The WASM engine runs in a Web Worker. The 3D view above keeps rendering at full frame rate while compression happens in the background.

Command-Line Parity

This tab is not a separate reimplementation. It runs the identical C++ core, compiled once to WebAssembly, that the scissorc CLI compiles natively.

$ scissorc squeeze drone_flight.txt drone_flight.csa
$ scissorc unsqueeze drone_flight.csa drone_flight.restored.txt

Same auto-detection, same quantization math, same wire format — verified against each other in this repository's own test suite, not just asserted here.
