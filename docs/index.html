01 / THE PROBLEM

Machines generate spatial data faster than links can carry it.

A drone's IMU and vision stack, a robot's joint-and-pose stream, a LiDAR scanner sweeping a site — all of it is 6-DOF pose or point geometry, sampled far above the rate a constrained radio link was designed for.

02 / THE BOTTLENECK

Bandwidth becomes the constraint, not compute.

LoRa tops out near 27 kbps. A degraded 5G edge link can fall to a few hundred kbps. Satellite uplink is metered by the byte. General-purpose compression (gzip, zstd, lzma) treats this data as an undifferentiated byte stream and leaves real structure on the table.

03 — 04 / THE APPROACH & THE CODEC

Model the kinematics, not just the bytes.

Position, calibrated rotation, and point geometry each compress differently once you know what they actually represent. That's the entire bet this codec makes.

Schema-less
Point/pose/general shape is inferred directly from the data itself — no protobuf or JSON schema to define or version.
No GC pauses
The compression hot path runs in WASM linear memory with manual malloc/free, not JS object allocation — nothing for a garbage collector to pause on mid-compression.
Off the main thread
The WASM engine runs in a Web Worker. The 3D view above keeps rendering at full frame rate while compression happens in the background.

Auto-Optimize: search for a configuration from a real error budget

Instead of picking a quant_step and checking whether the resulting error happens to be acceptable, state the error you can tolerate and this searches the codec's real quant_step parameter space (an actual compress+decompress+measure at each candidate, not an estimate) for the strongest compression that stays within it — falling back to true lossless, honestly, if even the finest lossy step exceeds your budget.

Where this fits

  • 6-DOF pose streams (drones, robots, AR/VR headsets) — beats general-purpose compressors on three independent real ground-truth datasets, lossless.
  • Real ROS2 PoseStamped telemetry — MCAP's own default zstd container is measured larger than raw packed data on 2 of 3 real datasets; CSA is smaller on all three.
  • Bandwidth-constrained links (LoRa, degraded 5G, satellite) where every byte saved is transmit time saved.
  • GPS-style 2D tracks — beats lzma -9 and even a purpose-built lossy format (Google Encoded Polyline) while staying exact.

Where CSA loses — honestly

  • Specialized point-cloud formats: LASzip (industry-standard LAS/LAZ) beats CSA on the same real LiDAR scan, 87.8% vs. 84.0% smaller, and is far faster. WHY_NOT_ZSTD.md →
  • Aggressively-quantized lossy point clouds: Draco at its roughest setting produces a smaller (lossy) file than CSA's exact result — expected, since lossless can't beat sufficiently aggressive lossy.
  • Arbitrary files with no spatial structure — logs, source code, JSON. CSA's general-purpose fallback loses to zstd -19 on both size and speed on a real 18MB C++ source corpus. Not a defect; it's the trade-off of a codec built around kinematics instead of generic entropy coding.
07 / THE APPLICATIONS

Where the trade-off is worth it.

01

Autonomous robotics

High-frequency pose and joint-state streams without saturating the network the rest of the fleet depends on. This is the exact shape of data the pose benchmarks above measure.

02

Drones

Telemetry bandwidth is the actual constraint on long-range links (LoRa, degraded 5G) — see the Edge Link Simulator above for the real byte-count trade at each bitrate.

03

AR / VR

Compact 6-DOF motion streams for headset and controller pose, where calibrated-rotation quantization (the "rotation precision" slider above) is a first-class parameter, not an afterthought.

04

Industrial LiDAR & mapping

Point-cloud geometry compression that stays exact when it needs to — and, per the "where CSA loses" section above, loses honestly to specialized formats when a purpose-built codec already exists for the job.

09 / THE DEVELOPER EXPERIENCE

Same core, on the command line

This tab is not a separate reimplementation. It runs the identical C++ core, compiled once to WebAssembly, that the CLI and Python bindings compile natively.

ShellPython
# CLI -- cli/main.cpp, compiled natively
$ scissorc squeeze drone_flight.txt drone_flight.csa
squeeze: drone_flight.txt (126,952 bytes) -> drone_flight.csa (3,066 bytes), 97.58% smaller, lossless
$ scissorc unsqueeze drone_flight.csa drone_flight.restored.txt

# Python bindings -- bindings/python/csa.py (Apache-2.0, pip install .)
$ git clone https://github.com/samfrazerdutton/collapsible-scissored-surfaces-algorithm-.git
$ cd collapsible-scissored-surfaces-algorithm- && pip install .
>>> import csa
>>> blob = csa.compress_pose(poses)          # exact / lossless
>>> blob = csa.compress_pose_lossy(poses, pos_quant_step=8, quat_quant_step=8)

Same auto-detection, same quantization math, same wire format — verified against each other in this repository's own test suite, not just asserted here. Format spec: FORMAT.md.
